# Overview

The Todo REST API is a lightweight backend service that enables client applications to manage a collection of todo items through standard HTTP endpoints. It provides the essential operations needed to track tasks: listing all existing todos, creating new ones, and deleting those that are no longer needed.

The target users are application developers who need a simple, reliable task-tracking backend to integrate into web, mobile, or command-line clients. The system emphasizes simplicity, predictable behavior, and clear error handling over advanced features.

The high-level approach is to expose a small set of resource-oriented endpoints that operate on todo items, persist data reliably between requests, and return consistent JSON responses suitable for programmatic consumption.

# Capabilities

## Todo Data Model
- Each todo must have a unique identifier that is generated by the system on creation.
- Each todo must have a title field containing human-readable text describing the task.
- Each todo must have a completion status indicating whether it is done or pending.
- Each todo must record a creation timestamp.
- Titles must be non-empty and limited to a reasonable maximum length (e.g., 255 characters).

## List Todos
- The API must provide an endpoint to retrieve all existing todos.
- The list response must return todos as a JSON array.
- Each item in the list must include id, title, completion status, and creation timestamp.
- The endpoint must return an empty array (not an error) when no todos exist.
- The endpoint must respond with HTTP 200 on success.

## Create Todo
- The API must provide an endpoint to create a new todo from a JSON request body.
- The request must accept a title field and treat completion status as optional (defaulting to pending).
- The system must reject requests with missing, empty, or invalid title fields with HTTP 400.
- Successful creation must return HTTP 201 with the full created todo, including its generated id.
- Created todos must immediately be retrievable via the list endpoint.

## Delete Todo
- The API must provide an endpoint to delete a specific todo by its identifier.
- Successful deletion must return HTTP 204 with no response body.
- Attempting to delete a non-existent todo must return HTTP 404 with a clear error message.
- Deleted todos must no longer appear in subsequent list responses.

## Error Handling and Responses
- All error responses must return JSON with a clear, human-readable message field.
- The API must use standard HTTP status codes consistently (200, 201, 204, 400, 404, 500).
- Malformed JSON request bodies must produce HTTP 400 with a descriptive error.
- Unexpected server errors must return HTTP 500 without exposing internal details.

## Data Persistence
- Todo data must persist across API restarts.
- Concurrent requests must not corrupt the stored data.
- Identifiers must remain stable and unique for the lifetime of each todo.

## Non-Functional Requirements
- All endpoints must respond within 500 milliseconds under normal load.
- All request and response bodies must use JSON with UTF-8 encoding.
- The API must handle at least 50 concurrent requests without failure.
- The API must log each incoming request with method, path, and status code for observability.
- The API must provide a basic health-check endpoint returning HTTP 200 when operational.
